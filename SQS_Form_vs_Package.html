SQS - Form Score vs Package Score

How each is calculated, why they can differ, and a step-by-step test you can run yourself.
Primble - ACORD Form Processing Platform

The one-line summary. Form SQS answers "how good is THIS form on its own?" Package SQS answers "how good is the WHOLE submission - all forms averaged together, AND do the forms and documents agree with each other?" The package carries one thing a single form never can: consistency across documents and forms.

1. The shared engine (6 pillars)

Every SQS - form or package - is built from the same 6 weighted pillars:

PillarWeightWhat it measures
Structural Completeness25%Are the required core fields filled?
Exposure Consistency25%Do the exposures / numbers agree?
Property Integrity (COPE)15%Construction, Occupancy, Protection, Exposure present?
Loss History Alignment15%Loss runs present and matching the insured?
Umbrella Adequacy10%Umbrella limits sufficient (or N/A - weight redistributed)
Narrative Quality10%Is the supporting narrative substantive?
Score = (P1 × 0.25) + (P2 × 0.25) + (P3 × 0.15) + (P4 × 0.15) + (P5 × 0.10) + (P6 × 0.10)

The percentages are importance weights, not a bias. Structural & Exposure matter most (25% each); Umbrella & Narrative least (10% each). If Umbrella is N/A, its 10% is redistributed across the other five.

2. Caps - the key concept

A cap is a ceiling that overrides the weighted score when something is wrong. A cap cuts the score down - it never adds to it. Think of it as a speed limit, not a tax.

Stop typeCeilingMeaning
Hard stop60Score cannot go above 60 until resolved
Soft stop / warning85Score cannot go above 85 until resolved

If a form computes to 92 and a hard stop fires, it becomes 60. If it was already 55, the 60 cap does nothing (already under the ceiling).

3. Scenario A - ONE form selected

Form SQS

1 Compute the 6 pillars for that one form.
2 Weighted-sum them.
3 Apply form-level caps: its own field-level hard/soft stops + its own structural gates (COPE-zero, umbrella-fail, property).

The form only knows about itself.

Package SQS

1 Anchor to the form's finished score (zero rounding noise - they line up cleanly).
2 Apply package-only caps - cross-document checks the single form can't see: building value differs across documents, FEIN / insured-name mismatch across docs, any package-level hard/soft stop.
Honest result for one form:
- No package-only issue → Package = Form (correct - nothing extra to penalize).
- A cross-document issue fires → Package drops below Form (capped at 60 or 85). The gap is real signal: "the form looks fine, but the documents behind it disagree."

4. Scenario B - MULTIPLE forms selected

Each Form SQS

Exactly like Scenario A - each form scored on its own, in isolation. Form 125 doesn't know Form 130 exists.

Package SQS (built one pillar at a time)

1 Average each pillar across all forms: Package Structural = mean(125 structural, 130 structural, ...), and the same for all 6 pillars.
2 Weighted-sum those 6 averaged pillars (25/25/15/15/10/10).
3 Apply cross-form caps (e.g. "FEIN differs across forms", "building value differs across documents").

The package is not an average of the form headlines - it averages the pillars, then weights them. A weak form drags the averages down, so the package reflects the whole submission's health.

6. Test it yourself - make ONE form's Package differ from its Form

Goal: Select a single form and force the Package SQS to drop below the Form SQS, proving they are computed independently. The lever a single form exposes is a cross-document conflict - the package sees it, the form does not.

Method 1 - Building-value conflict across documents (most reliable)

  1. Start a fresh session and upload two documents for the same insured where the building value differs between them (e.g. one declarations page says $2,000,000, another says $3,500,000 for the same location).
  2. Select one property form only - ACORD 140 (Property) or ACORD 125.
  3. Generate the form and open the SQS panel.
  4. Expected: the conflict is flagged in data-consistency (property_building_value marked review-required). This becomes a hard cross-issue that caps the Package at 60, while the Form keeps its higher score. The two numbers now differ - on purpose.
  5. Resolve the conflict (confirm the correct building value in the Data Consistency picker). The cap lifts and Package returns to equal the Form.

Method 2 - Watch them re-converge

  1. With the conflict present: Package < Form (package capped at 60).
  2. Confirm the correct value → recompute → Package = Form again.
  3. This proves the difference is driven entirely by the cross-document factor, not by random math.
What you should see in the UI:
- When clean: Form SQS and Package SQS show the same number.
- When a document conflict exists: Package shows a lower number (capped at 60 for a hard conflict, 85 for a soft one) and the Form stays where it was.
- The on-screen note - "Form SQS rates each form on its own. Package SQS rates the whole submission and includes cross-form checks, so the two can differ" - is exactly this behavior.

Why this is the right test

A single form's scorer has no way to compare two documents to each other - consistency is a relationship between documents. Only the package layer runs that comparison. So the only honest way a one-form package can differ from its form is a cross-document / cross-form finding - which is precisely what these steps trigger.
