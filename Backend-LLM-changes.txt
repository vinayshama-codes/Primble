FILE 5: backend/services/pdf_service.py
--------------------------------------------------------------------------------
WHAT WAS ADDED/CHANGED:

  a) Added `Any` to typing imports (line ~7)

  b) Added Pass 1.5 block inside map_facts_to_form() — between the end of
     Pass 1 (deterministic rules) and the start of Pass 2 (GPT call).
     Gated by: if ENABLE_ALIAS_STAMPING
     Imports alias_stamper only if flag is on.
     Effect: fills additional fields from facts without an LLM call.

  c) Added new function compute_form_gaps(form_id, schema, facts):
     - Runs Pass 1 + Pass 1.5 only (no LLM)
     - Returns (mapped, unmatched, deterministic_filled)
     - Used by select_forms_bulk to compute what each form still needs

  d) Added new function combined_gap_fill(forms_to_unmatched, facts, raw_text):
     - Deduplicates field names across all selected forms
     - Batches fields into groups of 100 (_COMBINED_FIELD_BATCH) per LLM call
     - Passes the FULL raw_text to each batch — _fill_unmatched_with_gpt handles
       its own chunking so the entire document is always scanned
     - Distributes results back to each form that asked for each field

  e) map_facts_to_form() signature changed:
     OLD: map_facts_to_form(facts, schema, form_id="", raw_text="")
     NEW: map_facts_to_form(facts, schema, form_id="", raw_text="",
                             pre_filled_gpt: Optional[Dict[str, Any]] = None)
     When pre_filled_gpt is provided, Pass 2 uses pre-computed values
     instead of making a per-form LLM call.

  f) Added three new module-level constants after _FORM_FILL_BATCH_RETRIES:

       _FORM_FILL_MAX_TOKENS = int(os.getenv("FORM_FILL_MAX_TOKENS", "16000"))
         WHY: Without this cap, OpenAI returns JSON for ALL fields including nulls
         in json_object mode (~174k output tokens for 1531 fields). The TPM limit
         is 200k/min — one call saturated the entire per-minute budget, causing
         every subsequent call to hit 429 and wait ~52 seconds.
         NOTE: max_tokens is the OUTPUT cap, not the input context (128k).
         16000 output tokens is more than enough for a 100-field batch response.

       _COMBINED_FIELD_BATCH = int(os.getenv("COMBINED_FIELD_BATCH", "100"))
         WHY: 1531 deduplicated fields × ~400 chars/field = ~612k chars fields
         block. The budget calculation inside _fill_unmatched_with_gpt left only
         ~33k chars for raw text per chunk → 22 chunks instead of ~3. Batching
         at 100 fields keeps the fields block ~40k chars, restoring ~200k chars
         of raw text budget per chunk.

  g) In _call_llm_sync(): added max_tokens=_FORM_FILL_MAX_TOKENS to the
     _client.chat.completions.create() call.

  h) In chunk dispatch block: changed
       OLD: _chunk_pool_size = min(len(raw_chunks), 4)
       NEW: _chunk_pool_size = 1 if len(field_list) > 200 else min(len(raw_chunks), 4)
     WHY: All chunks were dispatched in parallel. candidate_counts (which tracks
     already-filled fields for progressive narrowing) is read at dispatch time,
     before any results return. So every chunk saw all 1531 fields as unfilled —
     progressive narrowing was completely dead. Sequential dispatch (max_workers=1)
     for large field sets also prevents simultaneous flood of API calls that
     triggered constant 429 rate-limit errors.

TO REVERT:
  - Remove `Any` from typing imports
  - Remove the Pass 1.5 block in map_facts_to_form()
  - Delete compute_form_gaps() function
  - Delete combined_gap_fill() function
  - Revert map_facts_to_form() signature to remove pre_filled_gpt parameter
  - Revert the Pass 2 block to always call _fill_unmatched_with_gpt()
    (remove the `if pre_filled_gpt is not None` branch)
  - Remove _FORM_FILL_MAX_TOKENS and _COMBINED_FIELD_BATCH constants
  - Remove max_tokens=_FORM_FILL_MAX_TOKENS from _call_llm_sync()
  - Revert _chunk_pool_size = min(len(raw_chunks), 4)

CHANGES MADE IN THIS CONVERSATION (Session: Performance Fixes & Root Cause Analysis)
Date: 2026-05-29
Branch: ready-for-deployment-V1
File changed: backend/services/pdf_service.py ONLY
================================================================================

PURPOSE: Fix why the new combined gap fill pipeline was SLOWER (9+ min for 3 forms
on a 130-page doc) than the old per-form pipeline. Root cause analysis + surgical
minimal fixes. No rewrites. No new files. Full document coverage preserved.

All changes are in backend/services/pdf_service.py unless stated otherwise.

--------------------------------------------------------------------------------
CHANGE 1: _GPT_CALL_BUDGET_CHARS bumped 360,000 → 380,000
--------------------------------------------------------------------------------
CONSTANT:
  OLD: _GPT_CALL_BUDGET_CHARS = int(os.getenv("GPT_CALL_BUDGET_CHARS", str(360_000)))
  NEW: _GPT_CALL_BUDGET_CHARS = int(os.getenv("GPT_CALL_BUDGET_CHARS", str(380_000)))

WHY: The old 360k budget left the combined batches with a smaller doc text slot,
  pushing the 130-page doc (327k chars) from 1-2 chunks to 2-3 chunks per batch.
  Bumping to 380k gives ~20k extra chars per call for raw text, keeping most
  130-page batches at 2 chunks instead of 3. Confirmed ~95k tokens, well within
  gpt-5.4-mini's 128k context window.

TO REVERT: Change str(380_000) back to str(360_000).

--------------------------------------------------------------------------------
CHANGE 2: _COMBINED_FIELD_BATCH bumped 100 → 200
--------------------------------------------------------------------------------
CONSTANT:
  OLD: _COMBINED_FIELD_BATCH = int(os.getenv("COMBINED_FIELD_BATCH", "100"))
  NEW: _COMBINED_FIELD_BATCH = int(os.getenv("COMBINED_FIELD_BATCH", "200"))

WHY: At 100 fields/batch a 1000-field set produces 10 batches × 3 chunks = 30 LLM
  calls. At 200 fields/batch it becomes 5 batches × 3 chunks = 15 calls — exactly
  half. The sweet spot for a 271-page doc is ~250 fields; 200 is a conservative
  safe step. Beyond ~300 the fields block grows so large it forces extra chunks,
  cancelling the batch savings.
  NOTE: The env var COMBINED_FIELD_BATCH can be used to tune without a code change.

TO REVERT: Change "200" back to "100".

--------------------------------------------------------------------------------
CHANGE 3: New constant _COMBINED_BATCH_PAUSE_S added
--------------------------------------------------------------------------------
NEW CONSTANT (added after _COMBINED_FIELD_BATCH):
  _COMBINED_BATCH_PAUSE_S = float(os.getenv("COMBINED_BATCH_PAUSE_S", "2.0"))

WHY: At OpenAI Tier 1 (200k TPM), each ~87k-token combined call uses 43% of the
  per-minute budget. Without a pause, back-to-back batches drain the bucket and
  every subsequent call hits 429 and waits 10-52 seconds. A 2s pause between
  batches costs ~12s total but saves ~120s of cumulative 429 waits. Default is
  2.0s. Set COMBINED_BATCH_PAUSE_S=0 after upgrading to Tier 2 (2M TPM).

TO REVERT: Delete this constant line and remove the inter-batch sleep that uses it
  (see Change 6 below).

--------------------------------------------------------------------------------
CHANGE 4: Stronger omit-null instruction in LLM prompt
--------------------------------------------------------------------------------
LOCATION: _build_prompt() function, system prompt text

  OLD: "You may also simply omit a key if the value is not present."
  NEW: "You MUST omit keys whose values are absent or unknown — do NOT return null,
       None, or empty strings. Listing absent fields as null wastes output tokens
       and will cause the response to exceed the token cap."

WHY: The model in json_object mode was returning explicit null for every field it
  couldn't fill, burning ~174k output tokens per call and saturating the 200k TPM
  budget in a single batch. Stronger prompt language reduces null emission before
  the json_schema fix (Change 7) fully takes effect.

TO REVERT: Restore the original "You may also simply omit" wording.

--------------------------------------------------------------------------------
CHANGE 5: Real progressive narrowing — absorb between chunks, not after all
--------------------------------------------------------------------------------
LOCATION: _fill_unmatched_with_gpt() → chunk dispatch block (sequential path)

  OLD (broken): The sequential path used a ThreadPoolExecutor with max_workers=1.
    _absorb() ran after all futures completed, so chunk 2 still saw ALL fields
    as unfilled when it was dispatched — progressive narrowing was completely dead.

  NEW (fixed): Restructured the sequential path (_chunk_pool_size == 1) to a
    plain for-loop that calls _absorb() between chunks:

      if _chunk_pool_size == 1:
          for chunk_idx, raw_chunk in enumerate(raw_chunks):
              active_fields = [f for f in field_list if not candidate_counts[f]]
              if not active_fields:
                  break
              prompt = _build_prompt(active_fields, raw_chunk, chunk_idx, len(raw_chunks))
              result = _call_llm_sync(prompt)
              _absorb(result, active_fields, chunk_label=f"{chunk_idx + 1}/{len(raw_chunks)}")
      else:
          # existing parallel ThreadPoolExecutor path — unchanged

WHY: Chunk N+1 now only receives fields that chunk N didn't fill. On a 130-page
  doc this cuts chunk-2 active field count 30-50%, shrinking the prompt and
  freeing more of the budget for doc text. Full document coverage is preserved —
  every chunk slice is still processed; the loop just exits early if all fields
  are resolved before the last chunk.

TO REVERT: Replace the for-loop with the old ThreadPoolExecutor(max_workers=1) block.

--------------------------------------------------------------------------------
CHANGE 6: Inter-batch pause in combined_gap_fill()
--------------------------------------------------------------------------------
LOCATION: combined_gap_fill() → batch loop, before each batch except the first

  ADDED:
      if batch_idx > 0 and _COMBINED_BATCH_PAUSE_S > 0:
          _time.sleep(_COMBINED_BATCH_PAUSE_S)

WHY: Prevents the TPM bucket from being empty when the next batch starts its first
  chunk. At Tier 1 a 2s pause is not enough to fully refill (refill rate = 200k/60s
  ≈ 3.3k tokens/s), but it meaningfully reduces 429 frequency at batch boundaries.
  The pause constant is env-var tunable (COMBINED_BATCH_PAUSE_S).

TO REVERT: Delete these 2 lines and delete the _COMBINED_BATCH_PAUSE_S constant
  (Change 3 above).

--------------------------------------------------------------------------------
CHANGE 7: json_schema response format — forces model to OMIT nulls
--------------------------------------------------------------------------------
LOCATION: _call_llm_sync() — the openai client.chat.completions.create() call

  OLD:
      response_format={"type": "json_object"}

  NEW: Replaced with a json_schema that uses additionalProperties: {"type": "string"}
    (no null allowed), so the model is forced by the schema to omit absent fields
    instead of emitting "null". Falls back to json_object on model rejection:

      _schema_response_format = {
          "type": "json_schema",
          "json_schema": {
              "name": "form_fill_response",
              "schema": {
                  "type": "object",
                  "properties": {
                      "values": {
                          "type": "object",
                          "additionalProperties": {"type": "string"},
                      },
                      "raw_text_sourced": {
                          "type": "array",
                          "items": {"type": "string"},
                      },
                  },
                  "required": ["values"],
                  "additionalProperties": False,
              },
          },
      }
      try:
          resp = await _client.chat.completions.create(
              ...,
              response_format=_schema_response_format,
              max_completion_tokens=_FORM_FILL_MAX_TOKENS,
          )
      except Exception as _schema_err:
          logger.warning("gpt_fill: json_schema response_format rejected (%s) — "
                         "falling back to json_object for this call", _schema_err)
          resp = await _client.chat.completions.create(
              ...,
              response_format={"type": "json_object"},
              max_completion_tokens=_FORM_FILL_MAX_TOKENS,
          )

WHY: In json_object mode the model treats every asked-about key as a contract to
  return — it emits "null" for absent fields, burning tokens. The json_schema
  approach makes null a schema violation; the model is forced to omit absent
  fields entirely. In production logs (271-page doc run), `total_returned` was
  77-200 per chunk; with json_schema active it should drop to single digits on
  null-heavy batches, cutting output tokens ~10× and eliminating truncation risk
  under the 16k max_completion_tokens cap.
  CONFIRM: After restarting uvicorn, check chunk logs — total_returned should
  drop from 77-200 to <10 on null-heavy batches (e.g. Crime coverage fields
  when the doc is a GL submission).

TO REVERT: Replace the try/except block with the original single
  client.chat.completions.create(..., response_format={"type": "json_object"}, ...)

PERFORMANCE IMPACT OF SESSION 2 FIXES:
--------------------------------------------------------------------------------

  Root causes of the 9-minute regression on 130-page doc (after Session 1):
  1. _COMBINED_FIELD_BATCH=100 → 10 batches × 3 chunks = 30 LLM calls
  2. Progressive narrowing was broken (sequential path still used ThreadPoolExecutor;
     _absorb ran after all chunks, not between them) → chunk 2 carried all fields
  3. json_object mode: model emitted "null" for every absent field → ~174k output
     tokens per call → saturated 200k TPM → cascading 429s with 10-52s waits
  4. No inter-batch pause → TPM bucket empty at batch start → immediate 429

  After Session 2 fixes (130-page, 3 forms):
    5 batches × 2-3 chunks = ~12 calls → ~3.5 minutes observed

  After Session 2 fixes (271-page, 3 forms):
    ~8 batches × 3-4 chunks = ~28 calls → ~8-9 minutes observed
    Root cause of 271-page slowness: doc is 2× larger → more chunks per batch
    + Tier 1 TPM ceiling (200k/min) causes intra-batch 429s that 2s pause doesn't cover.
    Fix: upgrade to OpenAI Tier 2 (2M TPM, 5000 RPM) → set COMBINED_BATCH_PAUSE_S=0.
    Expected after Tier 2 + json_schema active: ~4-5 minutes for 271-page doc.
